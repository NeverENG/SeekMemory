# adapters: AstrBot Host Integration

## Responsibility

adapters translates AstrBot and DSH events, providers, and message sending into application ports. Host objects do not leak into core, recall, or app/runtime domain policies. `adapters/host_gateway/` owns transient `HostRequest` and the single Python inbound `RuntimeInput` projection, not authentication, scheduling or domain policy.

## Composition root

The standalone console has its own composition root in `adapters/console/runtime.py` and HTTP entry in `adapters/console/server.py`. It reuses management and recall services, existing stores, and PersonaPacks without loading the AstrBot SDK or starting chat, models, or maintenance workers. Its HTTP adapter owns authentication and loopback-origin checks; see [WebUI](webui.md).

On start, AstrBotPlugin builds Store, Cache, TreeService, Graph, HybridRetriever, Source-backed Buffer, CheckpointManager, application services, AgentRuntime, Jobs, WebRoutes, and background services. On stop, it stops background and management tasks, unregisters its own routes, saves the buffer, flushes checkpoints, and finally closes Store.

main.py defines the plugin entry point and delegates lifecycle; composition and wiring live in adapters/astrbot/plugin.py. AstrBotPlugin explicitly owns hooks and attention components instead of sharing host state through multiple inheritance. AstrBotHooks in adapters/astrbot/hooks.py maps host hooks to service calls: access decisions, input acceptance, memory injection, assistant-reply capture, post-send delivery recording, and runtime/tool observation. It does not implement extraction, capacity, or maintenance algorithms.

Start and stop share a lifecycle lock. Partial initialization releases resources already created. Shutdown waits for background and management tasks before saving buffers, flushing checkpoints, and closing storage, then clears services, workers, caches, and host references. Cancellation waits for cleanup before propagating, allowing a safe restart.

## Port adapters

- AstrBotRuntimeAdapter extracts facts through astrbot.events and projects through HostGateway, preserving existing scene, role, addressed, thread, and message-ID fields, and manages event-extra values for user/reply Source IDs, turn IDs, final recall IDs, and episode deduplication. Event time and process receipt time are recorded separately.
- AstrBotModelGateway provides ModelGateway for deferred replies.
- AstrBotActionPort provides both ActionPort and MessageSender: execute accepts ActionRequest and returns ActionResult; the existing send method delegates to execute and returns a boolean.
- ProviderChatModel wraps a host extraction/persona provider as ChatModel.
- SeekMemoryContextAdapter connects Runtime's MemoryContextPort to the existing RecallService.
- RelationshipReader returns one validated, content-free V2 snapshot per subject from Cache. AstrBot does not gate replies or inject a style directive from relationship state; the independent configured Runtime gate remains separate.

Action request text is transient execution input, never an ActionRecord audit field. Unsupported actions return unsupported_action; empty text, missing sessions, unavailable hosts, rejected sends, and execution errors have fixed reason codes. Host exception messages are not returned; cancellation propagates so runtime can recover. The adapter reports execution results without owning retries, audit deduplication, or terminal-state decisions.

AstrBot centralizes time conversion in utc8_time_hook in astrbot/time.py. User messages, normal replies, deferred replies, and runtime audit pass through this adapter hook before calling the existing RunRecorder. New timestamps use ISO strings with an explicit +08:00 offset; kernel read views retain the existing naive format. Fields, kernel interfaces, and database structure are unchanged.

AstrBotBuffer reuses Buffer admission and topic algorithms, while AstrBotSourceView reuses SourceStore queries. Both use the same hook for pending projections and recovered processed parents. Historical Sources are not rewritten. Offset-aware legacy values are converted; missing, invalid, and offset-free values are preserved without guessing the old machine's timezone or deriving absolute event time or queue age from them. Whether those old values were wrong, or derived memories need revision, requires a separate audit against the original environment.

Runtime decisions still use epoch timestamps independently of the OS timezone. Time adaptation does not change core, Buffer, extraction contracts, or nightly-maintenance scheduling configuration.

AccessService uses full session UMO, sender ID, owner/trusted configuration, and observe_groups to decide whether a message can be observed/recalled. Host event details are normalized only at this boundary; plugin composition owns config and database path.

## Current boundaries

When `runtime_gate_enabled` is explicit, AstrBotRuntimeAdapter maps `REPLY` / `must_reply` to `should_call_llm(False)`: the host parameter **prohibits the default model request**. Other actions map to `True`. A disabled gate leaves the existing host flag untouched. Relationship observation never changes this gate. This mapping preserves the host's wake, already-sent and provider checks; it does not enable independent plugin model requests.

Hook registration must use the real plugin module path, so callbacks stay discoverable after reload. Runtime tool filtering runs before a model request; a tool observation hook after invocation is not enforcement. Host API limitations and plugin startup failures are handled at the outer boundary and must not leak AstrBot dependencies into business modules.

## Loopback memory adapter

`adapters/loopback/runtime.py` composes the existing Store, Buffer, RecallService and StatusService; `adapters/loopback/server.py` owns localhost HTTP, token checks, request mapping and resource shutdown. `scripts/serve.py` only parses CLI arguments and preserves the existing `python scripts/serve.py --data-dir <dir>` command. This is an edge transport and composition root, not a core policy or a services use case, and it does not load the AstrBot SDK. The real service composes a process-local AgentRuntime in `adapters/loopback/runtime_ingress.py`: HostGateway projects user input, while the existing Buffer `/capture` path alone stores user and assistant Source evidence and reply links. `scripts/runtime_http.py` remains a separate bridge verification entry.

`/capture` stores Source and queues extraction, while `/recall` reads existing Artifacts. `/extract/plan` returns a runnable ChatRequest for a ready topic (204 when idle); `/extract/commit` accepts only a task issued by the current process and the matching Source IDs, using the existing validation and CAS write pipeline. Invalid model output remains queued for retry; unknown or consumed tasks return 409. An unfinished writeback keeps the task in memory and returns 503; GET plan never silently writes. Tasks are process-local: after a restart hosts must request a fresh plan. The contract test commits its own captured task without consuming other subjects; unextracted recall remains incomplete, not a passing end-to-end claim. Per-request `/recall` character and result limits can only narrow the service defaults without mutating shared configuration. HTTP errors do not echo underlying exception text; unauthenticated health checks do not disclose the local database path. Newly created data directories are owner-only, and token metadata is atomically replaced with owner-only permissions; callers must still protect any existing data directory they pass in. Stored formats, public configuration and endpoint paths are unchanged.

The loopback HTTP ingress in `adapters/loopback/server.py` and `bounded_io.py` keeps localhost binding and bearer authentication; request/event IDs are correlation or deduplication keys, not credentials. Authenticated POSTs require one valid `Content-Length` and reject chunked transfer; encoded JSON request bodies are limited to 8 MiB for `/extract/commit` and 4 MiB for other POST routes. The total header receive deadline is 2 seconds and the body receive deadline is 5 seconds: missing length returns 411, invalid length/JSON or premature EOF returns 400, excess size returns 413, and receive timeout returns 408. Errors never echo message bodies or tokens; connections with unread bodies are closed. Unauthenticated requests still return 401 first. Stored data and public configuration are unchanged. Legitimate requests exceeding these trial limits are rejected; hosts must use their existing failure path rather than treating them as saved. Memory work remains serialized: deadlines prevent indefinite stalls but do not guarantee that another request is served immediately during a partial request. The separate `scripts/runtime_http.py` verification entry does not inherit these transport guarantees.

The ingress trust boundary is narrower than HostGateway: the loopback listener verifies possession of its startup bearer token, not a remote identity, while host adapters (in-process AstrBot and the separate DSH client) are responsible for mapping verified platform identity into host claims. `HostGateway.project()` only maps those claims into RuntimeInput; a session ID, `subject_key`, message ID or event ID cannot replace the bearer or establish caller identity. Input size and receive deadlines belong to the loopback HTTP adapter; prompt trust belongs to #165, disclosure to RecallService, and scheduling to AgentRuntime. A stalled authenticated local caller can still occupy the single worker until the bounded receive deadline; operation execution is not covered by that deadline. `scripts/runtime_http.py` is a separate verification server, not covered by these memory-listener limits; deploying it as a production service requires a separate owner/threat-model decision and review.

The 4/8 MiB ceilings are trial transport limits, not measured production percentiles. Byte-size examples from the actual DSH `KernelClient` JSON serialization (synthetic content, **not production traffic**): a 25,000-character Chinese `/capture` sample is 75,077 bytes, a 1,400,000-character sample is 4,200,103 bytes and exceeds the 4 MiB limit, a 200,000-space `/extract/commit` sample is 200,050 bytes, and a 1,900-character Chinese `/persona` sample is 5,744 bytes. Real-host payload distributions and slow-client frequency must be measured using route-level byte counts and timing **without bodies, tokens or identifiers** before claiming these trial limits fit production. The real-listener DSH contract test confirms that a rejected capture is not reported as saved, does not enter the extraction queue, and a subsequent valid message still succeeds; an early close with unread request bytes can appear to the DSH client as either HTTP 413 or a connection reset (`kernel_down`), so hosts must not assume a guaranteed 413 response; it does not prove production compatibility or solve the separate verification server.

The loopback database is **one logical subject, multiple host clients**: `owner_umo` (default `loopback:default`) is the canonical subject key, not a platform-specific conversation/session ID. Configure every platform that shares this data directory to send the same stable `subject_key` (DSH: `subjectMode=fixed`, `subjectKey=<owner_umo>`); multiple clients may capture, plan, recall and read the same shared Persona. Missing keys retain the legacy owner default; an explicitly different key receives `403 subject_mismatch` before any capture, recall, Persona read or task issuance. This does not make separate AstrBot and loopback processes share a coherent live cache, and it is not multi-tenant isolation: a database previously populated by several subjects must be audited/separated before reuse; unknown-provenance old Artifacts are not silently reassigned. No stored data or config keys change. Reverting this guard reopens cross-subject reads. For checks against this real service, pass `--subject <owner_umo>` to the DSH contract/smoke scripts; their mock defaults stay unchanged. See #198.
## DSH runtime bridge

DSH RuntimeBridge reuses KernelClient's authenticated loopback connection. After healthz advertises runtime_contract: 1, POST /runtime/events carries inputs, replies, deliveries, errors, and action execution results; POST /runtime/context obtains MemoryContext. app/runtime/contracts/ owns the public fields, and Python and Node both validate shared nonempty examples. Known millisecond or offset-aware event times map to epoch seconds; unknown time is 0 without guessing a historical timezone.

subject_key identifies stable memory ownership, while session_id identifies the runtime conversation. Pre-step uses a Source receipt and event time only when the message ID matches. Only an explicit server runtime_gate_enabled enables mapping its RunDecision to host admission or rejection; the bridge has no separate attention policy.

Legacy or unsupported runtime services retain capture/recall. Once a runtime write is attempted, failure or timeout never triggers a legacy capture, preventing duplicate writes. An ordinary assistant/message maps only to record_reply; without confirmed delivery it does not call record_delivery. The bridge adds no model loop, scheduler, proactive sender, or tool execution. The real `scripts/serve.py` now serves runtime events and contexts with `runtime_gate_enabled=false`; decision state is process-local and not restart-durable. Context reuses RecallService disclosure and explicit DSH `budget_chars`/`k` limits; wrong-subject requests cannot read or write. `/runtime/context` and legacy `/recall` accept only a boolean when `private` is explicit, rejecting malformed types with 400 before disclosure. Omission still defaults to non-private and private respectively, preserving both routes. `scripts/runtime_http.py` remains an independent AgentRuntime verification composition.

Each DSH host context registers once. Unload removes hooks, aborts bridge requests, and clears context caches; late responses cannot inject. Node integration tests exercise both the real `scripts/serve.py` memory service and the independent `scripts/runtime_http.py` verification entry.

Relationship mode defaults to observe: `off` skips relationship maintenance, while `observe` and the legacy config value `enforce` currently consolidate verified events only, without changing reply availability or style. Relationship Artifacts remain excluded from Recall and the management catalog. Expression tuning requires separate review and explicit enablement.

## Explicit interfaces and host bindings

`adapters/domain.py` exports SDK-free shared persona-file and relationship adapters; `adapters/ports.py` reuses application protocols. `adapters/astrbot/domain.py` exports AstrBot integration entries and intentionally requires its SDK. SDK-free event/runtime/time/action/context mappings remain available at their original individual paths. `adapters/astrbot/ports.py` declares the finite `HookHost`, `ProviderHost` and `MessageHost` views.

Hooks/attention no longer forward arbitrary unknown attributes. Their `_bindings` property exposes only the documented typed host capability view; detached test adapters can bind the same fields locally. The host remains the single owner of readiness, services, repositories and runtime-audit cleanup timestamp. Hook-local tool correlation remains separate from host resource ownership.

| Files | Responsibility and effects | Logical complexity and coupling |
|---|---|---|
| `astrbot/plugin.py` | Construct resources in dependency order and close them in lifecycle order | High: composition root; no memory algorithms |
| `astrbot/hooks.py`, `attention.py` | Map callbacks and apply the existing runtime/access/interaction decisions | Medium/high: finite typed host view, no arbitrary forwarding |
| `astrbot/registration.py` | Stable callback module/name/priority/order | Low: SDK registration only; old hooks imports remain aliases |
| `astrbot/events.py`, `runtime.py` | Event/receipt/extra correlation mapping | Medium: no SDK event imports or persistence policy |
| `astrbot/actions.py`, `model.py`, `context.py` | Host sends/provider calls and explicit context-record forwarding | Low: narrow injected host capabilities |
| `astrbot/time.py`, `topics.py` | Existing UTC+8 read/write views and Source-backed topic candidates | Medium: conversion and queue views; no new time policy |
| `persona_packs.py`, `relationship_policy.py` | Authored local files and validated relationship projections | Medium: format/access rules remain in their existing owners |

`tests/test_adapter_interface_contract.py` protects shared exports/protocols; runtime plugin tests protect finite dependencies and callback identity/order. Existing host lifecycle, cancellation, context, action and time-hook checks remain required. The UTC+8 implementation was compared as an AST with docstrings removed and is unchanged. Management routes and Node/frontend implementations are outside restructuring scope.

The host owns the observed bot identity used by background RunContext. Callback-only tool attempts belong to AstrBotHooks and are cleared after resource cleanup, so restart cannot complete an old tool receipt against a new executor. The host lifecycle regression covers identity capture, shutdown clearing and restart.

Committed-ID cache repair is shared through `app.CacheRepairs`; the composition root injects the same instance into checkpoint, extraction, context and maintenance writers. Business plans remain with each use case, and per-owner counts keep unrelated repairs out of checkpoint pending totals.
