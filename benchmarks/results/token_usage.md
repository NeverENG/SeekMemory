# Token A/B：完整历史 vs 短历史 + 检索

> **这不是离线基准。** 它真实调用 `deepseek-flash`，需要 `DEEPSEEK_API_KEY`，会产生费用（本次 54 次调用约 ¥0.01–0.03）。
> 复现：`python benchmarks/token_bench.py . --limit 9`

## 方法

- 语料来自 [`benchmarks/e2e.py`](../e2e.py) 的 60 天合成对话：844 条消息，其中 u0 私聊 240 行（约 3,174 字符）；
- 9 个问题 × 6 个配置 = 54 次调用，同一模型、`temperature=0`、`max_tokens=48`、`thinking` 关闭；
- 用量取 provider 返回的 `usage.prompt_tokens`，不做字数估算；
- 命中 = 回答中出现该题的期望关键词。

| 配置 | system prompt | 上下文 |
|---|---|---|
| `question` | 无 | 只发问题（下限） |
| `system` | 仅风格句 | 只发问题 |
| `persona` | 完整人设 | 只发问题 |
| `full` | 完整人设 | **全部历史** |
| `short` | 完整人设 | 最近 24 行 |
| `recall` | 完整人设 + 检索到的记忆 | 最近 24 行 |

`recall` 与 `short` 只差一个记忆块，两者的差值就是"记忆本身的代价"。

## 结果

| 配置 | 9 题 prompt_tokens | 平均/题 | 命中 |
|---|---:|---:|---:|
| `question` | 69 | 8 | 0/9 |
| `system` | 177 | 20 | 0/9 |
| `persona` | 303 | 34 | 0/9 |
| `full`（全部历史） | 23,154 | 2,573 | 7/9 |
| `short`（最近 24 行） | 2,670 | 297 | 0/9 |
| `recall`（24 行 + 检索） | 2,891 | 321 | **8/9** |

**相对完整历史：2,891 / 23,154 = 12.5%，即少 87.5% 的输入 token，命中 7/9 → 8/9。**

## 增量拆分（`recall` = 2,891）

| 组成 | token |
|---|---:|
| 问题本身 | 69 |
| 系统提示 | 108 |
| 人设 | 126 |
| 短历史（24 行） | 2,367 |
| **记忆注入** | **221（24.6/题）** |

省 token 的是历史截断（23,154 → 2,670，−89.7%）；**记忆本身是加项，平均每题多 24.6 token（+8.3% 于短历史基线）**，换来同长度基线 0/9 → 8/9 的命中。

## 限制

- **n=9**，题目固定，来自同一份合成语料；
- 240 行历史约 2,500 token，真实用户 60 天的历史远大于此；**比例会随历史变长而更大，但这个绝对值不代表线上账单**；
- 单模型（`deepseek-flash`）、`max_tokens=48`，回答很短，命中判定是关键词包含，不衡量回答质量；
- 最近 24 行窗口在"询问早期事实"的题目上天然 0 命中——这是设计意图（它就是要暴露滑窗的短板），不是巧合；
- **只统计问答请求。** 后台抽取、Dream、维护的 token 不在表内，那部分见 [`long_horizon.md`](long_horizon.md)。

原始逐题数据：[`token_usage.jsonl`](token_usage.jsonl)。
